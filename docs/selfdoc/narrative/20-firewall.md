# Граница private ↔ public

Проект живёт на двух полках. Репозиторий (то, что публикуется как навык)
везёт только машинерию: движок, сборщики, eval, `SKILL.md`. Личная доска
пользователя — состав советников, их корпуса, треки решений — живёт локально
и в git не уходит вовсе.

**Что gitignored и никогда не коммитится:**
- `advisors/*` — состав приватных советников и их корпуса (реальные живые
  люди + возможно копирайтные источники); тречены только `!advisors/README.md`.
- `principis.md`, `relationship.md`, `principis_corpus/` — модель самого
  пользователя (кто он перед советом) и приватные треки решений.
- `council/` — реальные заседания на настоящих решениях пользователя.
- `gov_heads.local.json` — локальный реестр эталонных якорей ИМЕННО
  приватных советников (`advisors/*`); в git трекается только
  `gov_heads.json` для шипуемых `lenses/*`.
- `board_config.json`, `reference-library-raw/`, `reference-library/`,
  `*-raw/` — сгенерированный конфиг и сырые копирайтные исходники, из
  которых собираются приватные советники.

**Что шипуется публично** — только public-domain: `lenses/<name>/` с
`corpus.jsonl` из источников вроде Gutenberg (например, дословные максимы
Сунь-цзы в `lenses/strategist/`), плюс сама машинерия скилла. Принцип: «корпус
собирает каждый сам» — навык не качает копирайтные книги, и дистрибутив не
несёт ничьих реальных имён.

**Механизация.** `scripts/firewall_check.sh` + pre-push git-хук выводят
приватные имена из локального `advisors/*` и не дают запушить их наружу —
fail-closed: если чек не прошёл, push блокируется.

**Урок из истории проекта.** Аудит перед публикацией (статический анализ
секретов/PII/копирайта) прошёл чисто — но первый живой прогон полного стека
вскрыл ДВЕ приватные утечки, которых аудит и синтетика не увидели: сырые
копирайтные книги для сборки советников оказались вне gitignore, а
единый реестр якорей писал реальные имена приватных советников наравне с
шипуемыми линзами. Обе закрыты (расширение gitignore + расщепление реестра
на трекаемый и локальный). Вывод: приватные утечки рождаются от РЕАЛЬНОГО
использования, а не от синтетических тестов — поэтому периодический
firewall-чек перед каждым push к публикации обязателен, а не разовый ритуал.
