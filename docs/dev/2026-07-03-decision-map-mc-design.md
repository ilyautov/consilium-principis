# Спека: карта решения → сценарии → Монте-Карло («Principis-расчёт»)

Дата: 2026-07-03. Статус: дизайн утверждён в брейнсторме, ждёт ревью юзера → план имплементации.
Контекст: смежный трек роадмапа Moat v2 (docs/dev/2026-07-02-moat-v2-roadmap.md, раздел «Смежный трек»).

## Цель

Говённый запрос не парсят — его **допрашивает совет**. Формализуем допрос Режима B до
«карты решения», добавляем сценарный слой (2×2, pre-mortem) и детерминированный
Монте-Карло-движок. Выход — синтез совета, где мнения советников (🔵/🟢/🟡) и «📐 расчёт»
стоят рядом, но не смешиваются, и запись в петлю исхода с прогнозом.

**Несущие принципы (не обсуждаются):**
- **Ноль LLM в счёте.** LLM элицитирует модель; считает только код, с сидом, детерминированно.
- **Все числа юзерские.** Совет выбивает диапазоны вопросами («худший реалистичный? типичный?
  лучший?»), но каждая величина имеет `confirmed_by_user` и без него не считается.
- **LLM рассуждает — код решает.** Паттерн двухфазного протокола: хост ведёт допрос,
  сервер валидирует карту (fail-closed) и считает.
- **Лейбл честный.** «📐 расчёт» ≠ истина и ≠ 🟡-экстраполяция; это модель юзера,
  прогнанная N раз. Рамка выхода всегда: «модель твоя: K величин, подтверждены тобой, сид S».

**Утверждённые развилки брейнсторма:**
- Одна спека end-to-end, режем на фазы (не три отдельных спеки).
- N=1 догфуд: продуктовое решение юзера (куда вкладывать время) — быстрая петля, считаемые
  величины; схема карты при этом универсальная.
- Архитектура: сервер-валидатор (схема + `validate_map` + `mc_run`), не state-машина допроса
  и не «чистый хост».
- UX: углубление Режима B (не новый режим): вопрос-РЕШЕНИЕ → круглый стол наполняет карту;
  МК — опциональный финал перед синтезом.
- Формулы: LLM пишет → юзер визирует; few-shot примеры моделей в INSTRUCTIONS;
  шаблоны-как-код — Фаза 5+, триггер = повторяемость форм моделей в журнале решений.

## 1. Карта решения — схема

`decision_map` (JSON; сервер — единственный владелец схемы):

```json
{
  "question": "одна строка — суть решения",
  "options": [
    {"id": "ship_public", "name": "…", "description": "…",
     "reversibility": "one-way|two-way"}
  ],
  "uncertainties": [
    {"id": "traction_prob", "kind": "event", "prob": 0.3,
     "confirmed_by_user": true, "elicited": "цитата ответа юзера"},
    {"id": "hours_to_ship", "kind": "continuous", "unit": "часы",
     "min": 20, "mode": 40, "max": 90,
     "confirmed_by_user": true, "elicited": "…"},
    {"id": "upside_hours", "kind": "continuous", "unit": "часы",
     "min": 50, "mode": 150, "max": 400,
     "confirmed_by_user": true, "elicited": "…"}
  ],
  "stakes": {"metric": "ценность в часах|деньгах|P(успех)", "direction": "max|min"},
  "horizon": "3 месяца",
  "situational": {"you": "…", "opponent": "…", "stance": "comp|coop"},
  "model": {
    "ship_public": "traction_prob * upside_hours - hours_to_ship",
    "_описание": "формула словами, как её видел и подтвердил юзер; все id — из uncertainties"
  }
}
```

- `options`: вариант «статус-кво / ничего не делать» обязателен — совет обязан его выбить.
- `uncertainties.kind`: `continuous` → треугольное распределение (min/mode/max),
  `event` → Бернулли (prob). Больше видов в v1 НЕ заводим (YAGNI).
- `situational` опционален (для конкурентных решений; родной для Макиавелли/Сунь-Цзы).
- `model`: по формуле на вариант; словесная версия хранится рядом — юзер визировал ИМЕННО её.

## 2. Гейты честности — `validate_map` (fail-closed)

Расчёт отказывается запускаться (тот же принцип, что no-manifest→A), если:
- хоть одна uncertainty без `confirmed_by_user: true`;
- `min ≤ mode ≤ max` нарушен, prob вне [0,1];
- нет `stakes` или `horizon`, меньше двух options, нет статус-кво-варианта;
- формула не парсится **безопасным мини-AST**: только `+ - * / ( )`, `min/max`,
  тернарный `if`, литералы и id величин из карты. Никакого eval, никаких имён извне.
  Неизвестный id → отказ (не ноль!);
- у формулы нет словесной версии.

Ошибки валидации возвращаются списком с человеческими формулировками — хост доносит их
до юзера как вопросы совета, а не как стектрейс.

## 3. `mc_run` — детерминированное ядро

Вход: валидная карта + `seed` + `n` (дефолт 10_000). Никаких вызовов LLM.
Тот же сид → тот же результат байт-в-байт (тестируемый инвариант).

Выход:
- на вариант: `mean, median, p10, p90`;
- попарно: `P(A > B)` по совместным сэмплам (неопределённости сэмплируются ОДИН раз
  на сценарий и подставляются во все варианты — иначе сравнение нечестное);
- `P(вариант лучший)` и `expected regret` (упущенное против лучшего в каждом сценарии);
- **sensitivity/торнадо**: вклад каждой неопределённости (корреляция сэмплов с исходом
  или low/high-своп) → top-2 неопределённости, которые реально решают исход.

Реализация: stdlib `random.Random(seed)` (без numpy — скилл без зависимостей).
10k×(варианты×формулы) на нашем AST — доли секунды, этого достаточно.

## 4. Сценарный слой — заседание, не счёт

- **Pre-mortem — ДО расчёта:** «прошёл год, вариант X провалился — почему?» Каждый советник
  отвечает из своего кернела. Продукт pre-mortem — недостающие неопределённости для карты.
- **2×2 — ПОСЛЕ расчёта:** оси = top-2 из торнадо. Совет разыгрывает 4 квадранта
  (что делаем, если оба плохо / оба хорошо / крест-накрест). Это формат заседания
  поверх Режима B, не вычисление.
- Петля слоёв: pre-mortem кормит карту → карта кормит МК → торнадо МК даёт оси 2×2 →
  квадранты 2×2 могут вскрыть новую неопределённость → уточнение карты (по желанию юзера).

## 5. Поток (углубление Режима B)

1. Юзер приносит запрос → допрос круглого стола как сейчас.
2. Хост распознаёт вопрос-РЕШЕНИЕ (есть выбор из вариантов) → предлагает карту
   («давай разложим до расчёта?»). Отказ = обычный Режим B, ничего не навязываем.
3. Допрос наполняет карту; совет выбивает числа тройками «худший/типичный/лучший»;
   формулы предлагает совет словами + выражением, юзер визирует.
4. Pre-mortem → правка карты.
5. `validate_map` → ошибки уходят юзеру вопросами → `mc_run`.
6. 2×2 по top-2 из торнадо (опционально).
7. Синтез: мнения советников и «📐 расчёт» рядом, лейблы не смешиваются.
8. Нудж петли исхода (§4.3, уже внедрён): запись решения обогащается `predicted`
   (из МК: P(успех) или ожидаемая метрика) + ссылкой на карту-артефакт.

Артефакт карты: `decisions/<дата>-<slug>.json` в корне доски (рядом с principis.md;
сохраняется только с согласия юзера — как все записи журнала).

## 6. Замыкание в петлю исхода и калибровка

- Запись журнала (шаблон §4.3) получает строку `Прогноз: 📐 <predicted> (карта: decisions/…)`.
- При резолюции ⏳ → ✅/❌ хост сравнивает predicted vs actual вслух.
- Накопление пар (predicted, actual) → калибровка юзера (диапазоны системно узкие/широкие;
  впоследствии Brier score). Это слой Principis: модель юзера растёт из его решений.
  В v1 — только хранение пар; счёт калибровки = существующий `calibration.py`.

## 7. Фазы имплементации

- **Ф1 (ядро, ноль LLM):** схема + `validate_map` + AST-парсер + `mc_run` + торнадо.
  Чистый код, TDD, полностью оффлайн-тестируемо. Ценность: можно считать руками.
- **Ф2 (элицитация):** MCP-тулы, INSTRUCTIONS (поток, few-shot формулы, тройки вопросов,
  правило визирования), лейбл «📐», point-of-use директивы.
- **Ф3 (сценарии + рендер):** pre-mortem и 2×2 как форматы заседания; Cowork-виджеты
  (гистограмма исходов, торнадо) через session_render-адаптеры.
- **Ф4 (петля):** predicted в записи журнала, карта-артефакт, сравнение при резолюции.
- **Ф5+ (по данным):** шаблоны-как-код, если журнал покажет повторяемость форм моделей;
  расширение видов распределений — только по реальной нужде.

Каждая фаза — своя ветка, ревью перед мержем (правило дуги Moat v2: адверсариальное ревью
несущее), оффлайн-CI-инвариант сохраняется.

## 8. Риски и открытые вопросы

- **Мусор на входе → уверенный выход.** Главный риск: юзер даёт шумные диапазоны, МК
  выдаёт наукообразную точность. Митигации: лейбл-рамка всегда; торнадо показывает,
  ЧТО решает исход (фокус на 1-2 величинах); калибровка петли со временем.
- **Анкоринг совета.** Совет НЕ называет числа первым — только выбивает. Правило в
  INSTRUCTIONS; нарушение ловится тем, что `elicited`-цитата обязана быть ответом юзера.
  (Слабая гарантия — хост может сфабриковать цитату; честность здесь на уровне
  host-тира, как в двухфазном протоколе. Аудит-механика — кандидат в Ф5+.)
- **Допрос утомляет.** Полная карта = 10-15 вопросов. Митигация: карта предлагается,
  не навязывается; можно остановиться на любой глубине — без полной карты просто
  нет расчёта, но есть обычный синтез Режима B.
- **Формула-визирование поверхностное** («да-да, считай»). Митигация: словесная версия
  формулы обязательна и произносится перед расчётом.

## 9. Критерий успеха (N=1)

Юзер прогоняет РЕАЛЬНОЕ продуктовое решение (куда вкладывать следующий месяц) через
карту→pre-mortem→МК→2×2→синтез→запись с прогнозом; через недели резолвит исход.
Оцениваем: (а) изменил ли расчёт решение или уверенность; (б) сошёлся ли прогноз;
(в) где допрос буксовал. Это решает «игры разума или продукт» для трека.
