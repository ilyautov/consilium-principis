# v0.1.2 Release and Dependency Refresh Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the post-v0.1.1 Windows/CI repairs, update the reviewed CI-only dependencies, and make a tagged release safely repeatable without mutating published assets.

**Architecture:** The release workflow derives one `RELEASE_TAG` from a tag push or an explicit manual input, checks out precisely that tag, and validates it before building. A rerun may create a missing release or validate its two existing immutable assets against the checked-out tag; it never overwrites a public release. Dependency updates remain hash-pinned and are validated locally and in the cross-platform GitHub Actions matrix.

**Tech Stack:** Python 3.10–3.12, pytest, npm/mcpb, GitHub Actions, GitHub CLI.

## Global Constraints

- Release version is exactly `0.1.2`; the tag is exactly `v0.1.2`.
- Preserve `server.json`'s source-tree `REPLACE-WITH-sha256-AT-RELEASE-TIME` sentinel.
- Keep build permissions read-only and restrict `contents: write` to the publish job.
- Keep all action references pinned to full commit SHAs.
- Existing release assets are immutable: validate the downloaded release assets on rerun and never use `--clobber`.
- Commits use Conventional Commit style in English.

    --artifact "$release_dir/consilium-principis.mcpb" \
    --registry-manifest "$release_dir/server.json"
else

    --repo "$GITHUB_REPOSITORY" --generate-notes
fi
