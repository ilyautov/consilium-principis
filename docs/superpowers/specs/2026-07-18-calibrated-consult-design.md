**Дата:** 2026-07-18
**Статус:** одобрен владельцем (brainstorming), готов к writing-plans
**Автор контекста:** Consilium-Principis

---

## 1. Проблема и позиция

Ров проекта бьёт ложь **МОДЕЛИ** (`citation_ability=1.0`, fail-closed отказ вместо
конфабуляции). Он НЕ бьёт оверрелайанс **ЧЕЛОВЕКА**. Это отдельная, измеренная ось:

> arXiv 2607.13562 (Marcoccia, Quattrociocchi, Capraro, N=3132, 4 preregistered):
> «Merely having access to AI nearly eliminated participants' willingness to suspend
> judgment» — доступ к ИИ почти обнуляет готовность сказать «не знаю», ДАЖЕ когда совет
> неверен и точность премируется; уверenность при этом почти удваивается.

Наш продукт — тоже ИИ-совет, оформленный убедительнее одиночного бота (несколько
авторитетов + дословные цитаты) → по логике статьи давит на воздержание СИЛЬНЕЕ.

**Ключевое ограничение метода.** Оверрелайанс — поведение ЧЕЛОВЕКА. Его нельзя замерить
оффлайн (нужны люди, как N=3132 в статье). Урок [[antisycophancy-phase1-negative]]: текстовый
нудж в INSTRUCTIONS даёт измеренный НОЛЬ (даже отрицательно); рычаг = детерминированный тул,
не текст; и поведенческую интервенцию нельзя шипить без замера эффекта.

**Отсюда позиция: это ИНСТРУМЕНТ, не интервенция.** Он не заявляет «снижаю оверрелайанс»
(недоказуемо оффлайн — это обход ловушки антисикофантики). Он делает твой оверрелайанс
ВИДИМЫМ: фиксирует твою позицию ДО совета, показывает сдвиг ПОСЛЕ, копит калибровку по
исходу. Ценность — зеркало на N=1 (сам владелец), плюс живые данные, из которых будущая
эффективность мерилась бы честно (не LLM-прокси).

**Северная звезда — провенанс+отказ.** Эту ось берём именно потому, что замер признал её
незакрытой, а все ретрив-рычаги исчерпаны замером ([[multiquery-fifth-null]],
[[moat-defect2-never-existed]]).

## 2. Архитектура

### 2.1 Модель захвата (opt-in режим, гейт по предусловию)

Отдельный режим **«calibrated consult»** — владелец явно его вызывает, когда хочет
замериться. Вне режима — обычный совет без трения.

Внутри режима — цикл `open → совет → close`:

1. **`open`** фиксирует ПРИОР (твою позицию + уверенность) ДО ответа совета.
2. Хост даёт ответ совета (как обычно, через существующие тулы/INSTRUCTIONS).
3. **`close`** фиксирует ПОСТЕРИОР (позицию ПОСЛЕ), считает и возвращает ЗЕРКАЛО.

**Честная граница гейта (load-bearing, в спеку явно).** Ответ совета производит ХОСТ
(Claude), не серверный тул: MCP-сервер — это stateless-тулы + INSTRUCTIONS. Значит сервер
НЕ может физически запретить хосту сгенерировать текст. Детерминизм достигается на уровне
ИНСТРУМЕНТА, не запрета: `close` fail-closed без записанного приора (нет `open` → нет
`consult_id` → закрывать нечего). Зеркало и калибровочный кредит доступны ТОЛЬКО через
gated-последовательность. Это сильнейшая детерминированная форма, которую допускает
host-side архитектура — и мы её так и называем, не переобещая.

### 2.2 Хранение

Записи в **`consults/`** — gitignored (личные данные, тот же паттерн, что `decisions/`;
NB: `decisions/` попал в .gitignore в этой же сессии, `972e41a`). Одна запись = один
консульт, имя `consults/<created>-<slug>.json` (форма decision_map/decision_card).

**`.gitignore`:** добавить `consults/`.

### 2.3 Схема записи

`id` = `cc_<ULID>` (переиспользовать `decision_card._ulid()` / Crockford base32; НЕ
дублировать реализацию — импорт или общий хелпер).

```json
{
  "schema_version": "1.0.0",
  "id": "cc_01J...",
  "created": "2026-07-18",
  "question": "<вопрос, который несёшь совету>",
  "prior": {
    "call": "<твоя позиция/ответ, свободный текст>",
    "confidence": 0.62,
    "abstain": false
  },
  "posterior": {
    "call": "<твоя позиция ПОСЛЕ совета>",
    "confidence": 0.80,
    "abstain": false,
    "followed_council": true
  },
  "mirror": {
    "confidence_delta": 0.18,
    "shifted": true,
    "abstention_dropped": false
  },
  "prediction": null,
  "outcome": null,
  "decision_card_ref": null
}
```

- `prior` пишется на `open`; `posterior` + `mirror` — на `close`.
- `prediction` — опциональный **resolvable-прогноз** по КОНТРАКТУ decision_card
  (event: `probability`; metric: `p10/p50/p90`, `unit`, `direction`). Даёт отложенную
  калибровку по исходу. Валидируется тем же кодом, что карта (реюз, не копия).
- `outcome` — заполняется позже тем же путём, что decision_card (`close_card`-подобно);
  кормит `prediction_calibration`.
- `decision_card_ref` — опц. ссылка `dc_…`, если консульт позже перерастает в решение.
  Машинерию promote НЕ строим (YAGNI) — только поле.

## 3. Тулы (MCP)

Оба — детерминированные, ноль LLM/сети, fail-closed, RU-ошибки аккумулируются (зеркало
`validate_card`: возвращаем ВЕСЬ список, не первую ошибку — хост задаёт их владельцу).

### 3.1 `calibrated_consult_open`
- **Вход:** `question: str`, `prior_call: str`, `prior_confidence: float [0..1]`,
  `prior_abstain: bool = false`.
- **Гейты:** непустые `question`/`prior_call`; `prior_confidence` ∈ [0,1] и число (не NaN/inf);
  `prior_abstain` bool. Нарушение → RU-список ошибок, запись НЕ пишется.
- **Успех:** пишет запись (только `prior`), возвращает
  `{"ok": true, "consult_id": "cc_…", "next": "спроси совет, затем calibrated_consult_close"}`.

### 3.2 `calibrated_consult_close`
- **Вход:** `consult_id: str`, `posterior_call: str`, `posterior_confidence: float [0..1]`,
  `posterior_abstain: bool = false`, `followed_council: bool`, `prediction: obj|null = null`.
- **Гейты (fail-closed):** `consult_id` существует и ещё НЕ закрыт (иначе ошибка); те же
  проверки полей, что в open; если `prediction` задан — валидируется контрактом decision_card
  (переиспользовать `decision_card.validate_card`-подмножество для prediction), иначе ошибки
  списком.
- **Успех:** пишет `posterior`, вычисляет `mirror`, опц. цепляет `prediction`, возвращает
  ЗЕРКАЛО (см. §4.1) + `{"ok": true}`.

### 3.3 Исход и калибровка (реюз существующего)
Отдельный новый тул для резолва НЕ обязателен, если `prediction` резолвится тем же путём,
что decision_card. Журнал калибровки — через существующий `prediction_calibration` (§4.2),
расширенный чтением `consults/`. Точную форму (реюз `outcome_loop` vs новый тонкий резолвер)
решает план — но БЕЗ дублирования Brier/MAE.

## 4. Сигнал оверрелайанса

### 4.1 Зеркало (немедленно, на `close`)
- `confidence_delta = posterior.confidence − prior.confidence` — arXiv: уверенность
  почти удваивалась; положительная дельта без роста точности = флаг.
- `shifted = (posterior.call != prior.call)` (нормализованное сравнение) — позиция сменилась.
- `abstention_dropped = prior.abstain && !posterior.abstain` — **ядро находки arXiv**
  («перестал говорить не-знаю» после появления ИИ-совета).

Зеркало возвращается владельцу текстом сразу — это и есть видимый выход инструмента.
Оно НЕ выносит вердикт «оверрелайанс» (сдвиг может быть честной коррекцией) — только
показывает факт сдвига/инфляции. Вердикт даёт лишь исход (§4.2).

### 4.2 Отложенная калибровка (по исходу, реюз `prediction_calibration.py`)
По закрытым+разрешённым консультам:
- **инфляция уверенности:** mean(`confidence_delta`);
- **подавление воздержания:** count(`abstention_dropped`);
- **bad-follow rate:** среди `followed_council=true` с разрешённым исходом — доля, где
  ПРИОР набрал бы лучше постериора (событие оверрелайанса). Считается на тех же
  Brier/log-score, что карты.

`calibration_journal` (существующая функция, `min_n=MIN_TRUSTWORTHY_N`) применяется к
консультам; малое n → честный «мало данных», не выдумка.

## 6. Обработка ошибок

- Всё — fail-closed, RU-строки, аккумулируются (не первая).
- Неизвестный/уже закрытый `consult_id` → явная ошибка (не тихий no-op).
- Битый `prediction` → ошибки контракта decision_card списком, запись не закрывается.
- Не-dict/None вход → ошибка (зеркало `validate_card`).
- Ноль LLM, ноль сети — как decision_card/decision_map.

- LLM-симуляция эффективности (отвергнутый вариант «замер-первый» — валидность LLM-юзера слаба).

- UI/визуализация.
- Авто-детект, когда включать режим (владелец вызывает явно).
- Мульти-юзер.
- Полный отдельный резолвер исхода, если хватает пути decision_card.
